# and-implementation-audit 程序项目实现侧审计

本 skill 校验程序项目**实现侧设计自洽**：判定标准全部在审计执行时从四类声明源（openspec/规范/架构/技术方案）运行时抽取，skill 不写死任何声明类型或路径。作为 and-design-system-audit（审设计文档体系）与 and-openspec-upstream-audit（审 change 与上游）的实现侧补充，回答「代码是否兑现设计、设计是否被代码落地」。

**本 skill 目录**：即本 `SKILL.md` 所在目录。`references/` 在此目录下。

## 适用范围（权威源：references/audit-criteria.md）

- 面向**程序项目**，由用户**手动触发**（输入为项目根目录），审计对象为项目整体实现侧设计自洽
- 判定为 **AI 语义判断 + 可机检规则确定性验证**，判定标准从四类声明源**运行时抽取**，skill **不发明规范、不裁决声明冲突**
- **只读不自动修**：审计只报告问题，不自动修改代码或文档
- **边界**：不审代码质量（风格/性能/坏味道本身，除非规范或设计有条款）；不审计 openspec change 的 diff 落地（openspec 流程职责）；不审计设计文档体系（and-design-system-audit）；不校验技术文章（and-validate-article）

## 四类声明源

| 源 | 抽取内容 | 定位依据 |
|----|---------|---------|
| ① openspec | `openspec/config.yaml` 的 `context` 目录结构（第一声明源）+ change 产物声明 | openspec 标准位置 |
| ② 规范 | 适用语言规范的命名/格式化/注释/常量规则 | 运行时经项目根 `AGENTS.md` 定位的适用规范 |
| ③ 架构 | 模块划分/技术选型/数据模型/部署/安全/集成声明 | 运行时经规范定位的架构类文档 |
| ④ 技术方案 | 包名规范/实现决策 | 运行时经规范定位的技术方案类文档 |

**各声明源的具体文件与路径在运行时经项目根 `AGENTS.md` 定位规范后确定，skill 不写死任何声明类型或路径。**

每条抽取必引「声明源文件+位置」，供人工覆核。源缺失按「该层不存在」缺位处理，不误报存在性缺失。

## 工作流

### Step 1：声明源抽取（门禁）

1. **读项目根 `AGENTS.md`**，判定项目类型（配置/文档/程序）；配置/文档项目无实现侧 → 按「该层不存在」声明缺位
2. **读四类声明源**，抽取声明与规则清单，每条必引「文件+位置」：
   - config.yaml `context` 目录结构（顶层职责/放置规则/禁止区）
   - 语言规范表格化规则（命名 camelCase/PascalCase/snake_case 等、格式化工具、行宽、常量命名）
   - 架构文档模块划分/技术选型/数据模型/部署/安全/集成声明
   - 技术方案包名规范/实现决策
3. **自检门禁**，命中任一即中断，输出「声明冲突清单」不审计代码：
   - **冲突**：config.yaml 与架构文档对同一实体说法不一致（如模块数说法不一）
   - **空缺**：代码出现实体但四类声明源均无对应声明线索，且无法判定是声明缺失还是设计缺位
   - 命中 → 只报事实，不替设计拍板
   - 模型完备 → 进入双向对照

### Step 2：代码证据扫描

对照代码收集证据，**不写死任何类型/路径**，按项目技术栈选取可机检手段：

- 目录树/包结构（对照 config.yaml context 的第一声明源）
- 依赖清单（package.json / go.mod / pyproject.toml / build.gradle 等，对照技术选型声明）
- import 引用（对照实现决策/模块划分声明）
- 格式化工具运行结果（gofmt -l / black --check / prettier --check 等，对照格式化条款）

### Step 3：双向对照四态判定

```
声明 → 代码（覆盖）：声明有实现？  无 → 空头设计
代码 → 声明（依据）：实现有声明？  无 → 无依据；有但冲突 → 跑偏
两者均有且一致                        → 自洽
```

- **config.yaml context 为第一声明源**：代码中出现的实体须有 config.yaml context 声明的目录/包名对应才算有设计依据；粒度不足时报告标注「声明粒度不足，需人工确认」
- 机检规则（命名正则/格式化工具/行宽）确定性验证；语义规则（职责分离等）AI 判断
- 不审代码质量：无设计声明约束的结构问题（如冗长文件）不判不合规

### Step 4：报告

按**声明源分组**输出只读报告，每条 finding：

```
声明源 / 声明位置 / 判定态(自洽/空头设计/无依据/跑偏) / 现状 / 基于声明的修改方向
```

修改方向**必须保留声明自身的语气**：规范标 [必须] 写「按 §x 必须…」，标 [推荐] 才可写「按 §x 建议…」；规范未规定改法时引声明原文，不发明。报告**不引入严重度/优先级分级，不发明规范外的豁免**。

## 修复模式

审计**永远只报告**：代码不合规输出「声明源位置/现状/基于声明的修改方向」（保留 [必须]/[推荐] 语气），声明冲突只列冲突事实与涉及位置，**绝不自动改**代码或声明；怎么修由人决策。

## 输出语言

报告面向用户，使用简体中文；技术术语（openspec/roadmap/markdown 等）与代码标识符保留英文。具体边界：面向人阅读的内容（报告正文、判定态、问题描述）用简体中文；机器字段（路径、CLI flags、JSON 字段名）保留英文。
