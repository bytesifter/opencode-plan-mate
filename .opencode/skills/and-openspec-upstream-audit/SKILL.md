# and-openspec-upstream-audit openspec change 上游引用审计

本 skill 沿**运行时抽取的细化链**对新生成的 openspec change 做四维审计，确认 change 的产生不超出既有设计边界（避免「没设计就执行」）。三层校验，每层各司其职。

**本 skill 目录**：即本 `SKILL.md` 所在目录。`lint.py` 与 `references/` 均在此目录下。调用 `lint.py` 时须用本目录的绝对路径（运行时工作目录是用户项目，不是 skill 目录）。

## 适用范围（权威源：references/audit-criteria.md）

- 面向**新生成的 openspec change**，change 生成后由用户**手动执行**本 skill 验证
- **存量 change 不审计、不回填上游引用**；新规范从新 change 生效
- 细化链的层数、各层定义、各层文档落点、缺位规则**全部在审计执行时经项目根 `AGENTS.md` 定位规范后抽取**，skill 不写死任何层名、文档路径或关键字
- 配置/文档项目无对应层时，按「声明缺位但已说明」处理（proposal 已显式标注「该层不存在」）
- **只读不自动修**：审计只报告问题与修复方向，不自动改 change 或上游文档，修复由人决策

## 四维审计（权威源：references/audit-criteria.md）

| 维度 | 检查内容 | 检查层 |
|------|----------|--------|
| 存在性 | 抽取细化链中的各上游层是否都有对应；缺失是否已显式声明 | L1（确定性）+ L2 |
| 清晰度 | 每层是否比上层更具体（而非重复或模糊） | L2 |
| 粒度 | 细化粒度是否递增（方向→原则→形态→改动，以抽取规则为准） | L2 |
| 偏差 | change 是否超出/冲突上游设计（change 改了上游未说过的，或上游说了 change 未对齐的） | L3 |

## 工作流

### Step 0：规范定位与细化链抽取（门禁）

1. **读项目根 `AGENTS.md`**，定位其指向的规范体系（用户级 `AGENTS.md` 路径），判定项目类型（配置/文档/程序）
2. 从适用规范文本抽取**细化链模型**：层清单（每层 `id` / `label` / 文档落点模式 `patterns`）、层间顺序、哪些层对哪类 change 为必须、缺位声明规则。每条抽取**必引「规范依据（文件 + 条款）」**
3. **自检门禁**：文件树/架构文档/技术方案等落点在规范中说法冲突或空缺时，中断并只输出「规范问题清单」，不审计 change
4. 将层定义写入临时 `layers.json`（`[{"id","label","patterns":[...]}, ...]`），供 Step 1 使用

### Step 1：L1 上游引用完整性（确定性）

运行本目录下的 `lint.py`（**用绝对路径**），传入 Step 0 抽取的层定义：

```bash
python3 <本skill目录>/lint.py "<change目录>" --layers "<layers.json>" --format json
```

解析输出 JSON：`findings` 数组每条含 `layer/rule/severity/issue`，`summary` 含 errors/warnings 计数。

- 逐层检查 proposal 的 Why/Impact 是否引用对应上游文档锚点（锚点须在仓库中真实存在）
- 缺失层若 proposal 已显式标注「该层不存在」→ warning（声明缺位）；未标注 → error（存在性缺失）
- 无法定位规范或抽不出层定义时，**声明缺位并提示**，不臆断层、不退回内置层定义

### Step 2：L2 结构质量（AI 判断，存在性/清晰度/粒度）

按 `references/audit-criteria.md` 的四维判定标准，对照 Step 0 抽取的细化链评估：

| 子维度 | 检查要点 |
|--------|---------|
| 存在性 | 抽取链中的各上游层是否有对应（结合 L1 结果）；必须层缺失是否判硬性缺失 |
| 清晰度 | 每层是否比上层更具体；proposal 是否重复上游而非细化；design 是否给出上游未定的实现形态 |
| 粒度 | 细化粒度是否递增、无跳级（具体分层以抽取规则为准） |

输出每项：`维度 / 判断(通过/部分/缺失) / 依据(引用具体文档位置) / 修复建议`。给依据而非纯打分，允许人工覆核。

### Step 3：L3 一致性核查（AI 判断，偏差）

对照上游文档，核查 change 与上游设计的一致性：

1. **抽取 change 的实质变更**：proposal 的 What Changes、design 的 Decisions、specs 的 Requirements
2. **逐条对照上游**：该变更是否在上游已有声明、或与上游矛盾
3. **两类偏差各列出**：
   - **越界**：change 改了上游未说过的（引入上游未设计的行为/能力）
   - **未对齐**：上游说了 change 未兑现的（上游承诺的能力 change 未覆盖）
4. 每条输出：`变更点 / 上游对应位置 / 判断(一致/越界/未对齐) / 依据`

### Step 4：汇总报告

按四维输出结构化报告：

```
┌─ 审计报告 ──────────────────────────────────────────┐
│ change: <目录>                                       │
│ 细化链: <抽取的层清单，每条附规范依据>                 │
│ 四维: 存在性(通过/缺失)  清晰度(通过/部分/缺失)        │
│       粒度(通过/部分/缺失)  偏差(N 处)                │
├─ L1 引用完整性 ─────────────────────────────────────┤
│   - [ok/缺失] <层> ...                                │
├─ L2 结构质量 ────────────────────────────────────────┤
│   - 存在性: <判断> <依据>                             │
│   - 清晰度: <判断> <依据>                             │
│   - 粒度:   <判断> <依据>                             │
├─ L3 一致性 ──────────────────────────────────────────┤
│   - [越界]   <变更点> vs <上游> <依据>                │
│   - [未对齐] <上游承诺> vs <change> <依据>            │
├─ 红线 ───────────────────────────────────────────────┤
│   (命中任一即判偏差，需人决策修复方向)                 │
└──────────────────────────────────────────────────────┘
```

## 修复模式

审计**永远只报告**：L1/L2/L3 发现的问题只输出报告与修复方向（补引用 / 补上游 / 更新文档），**绝不自动改** change 或上游文档，修复由人决策。存量 change 即使审计也不回填上游引用。

## 输出语言

报告面向用户，使用简体中文；技术术语（openspec/roadmap/markdown 等）与代码标识符保留英文。具体边界：面向人阅读的内容（报告正文、维度名、问题描述）用简体中文；机器字段（代码、CLI flags、JSON 字段名、函数/变量名）保留英文。
